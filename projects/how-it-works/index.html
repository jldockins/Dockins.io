How these build logs are made

Every project on this site keeps a single file, BUILDLOG.md, that lives in the project's own git repository. It is the working file and the source of the published page — not a write-up done afterward. The page you read is generated from that file and rebuilt as the work happens, rather than written up at the end.

The problem it solves is specific. Working on a project with an AI coding assistant, the reasoning behind every decision lives in a conversation that disappears when the session ends. Come back after two weeks and the ramp-up costs as much as handing the project to a stranger. Writing the log as you go fixes that, and it happens to produce most of a good build write-up for free.

Why it lives in git

The log sits in the project's own repository, versioned alongside the firmware, the schematics and the photos. That is not incidental — it is what makes the rest work.

Committing the log with the code means the two cannot drift apart silently. Every entry has a commit behind it, so the log carries its own history: when a decision was made, what the state of the project was at the time, and what changed afterward. A decision that later got reversed is still visible, with its date, rather than quietly edited away.

It also makes the log auditable against reality. The session-open command reads the recent commit history and compares it against the newest entry — if code changed and the log did not, it says so before anything else happens. A build log that quietly falls behind the build is worse than none, because it is trusted.

And it means the work is backed up. Nine days of reasoning that exists only on one laptop is one spilled coffee from gone.

How a page gets here

Pushing to the project repository triggers a build: a script reads BUILDLOG.md, strips the private sections, renders the rest to HTML, copies the photos, and writes a small manifest describing the project's status. That output is committed into this site's repository, which triggers a second job that uploads the changed files over FTP to the host.

The index you came from is regenerated from those manifests, so a new project appears in the list without anyone editing a page. Status — in progress, paused, complete — is derived from the date of the most recent session rather than declared, because a status that has to be maintained by hand is a status that goes stale.

The point of all of it is that publishing is not a step. There is no moment where the documentation gets written up, which is the moment it would otherwise not happen.

What is public and what is not

The log holds more than the page shows. Current state, the next action, and the raw session journal stay private — nobody needs to read a scratchpad. What publishes is the premise, the reasoning, the bill of materials, the build steps, the measured results, the questions, and the things that went wrong.

That last one is deliberate. Dead ends and open questions are published as-is. A build log that only shows the path that worked is a brochure.

The commands

These are slash commands for Claude Code. Each one edits BUILDLOG.md directly.

CommandWhenWhat it does
/log-initStarting a project Interrogates the premise, the constraints, the build phases, and — the part that matters — what the project is deliberately not. Pushes back if the finish line is vague.
/log-adoptAfter a planning session Turns a project brief written elsewhere into a build log, without re-asking anything the brief already answers.
/log-openStart of every session Cold-start briefing: the premise, the non-goals verbatim, where the work stopped, the single next action, live constraints, and any past dead end the next action risks repeating. Also checks the log against git and flags work that was never logged.
/log-stepA build step is finished Writes the step into the published walkthrough — what was done, why that way, what verified it, and the photo. Refuses steps that aren't actually done.
/log-askA question comes up Records a question and the thinking around it, open or settled. Open questions publish as open.
/log-noteMid-session Catches a decision, a part substitution, or a reference without breaking flow.
/log-closeEnd of every session Writes the session in, rewrites the current state so it stands alone, and records decisions, dead ends, measurements, and completed steps.
/log-publishBefore a public release Drafts the reader-facing narrative from the working log.

The loop

1. Plan. Work out the premise, the constraints, and the non-goals in conversation. Write it into a brief.
2. Adopt. /log-adopt turns the brief into the log. Nothing gets re-litigated.
3. Open. Every session starts with /log-open, so a two-week gap costs a paragraph instead of an afternoon.
4. Work. /log-step when something is finished, /log-ask when a real question comes up, /log-note for everything else.
5. Close. /log-close before stopping. This is the one that matters most, and the one easiest to skip.
6. Push. The commit carries the log and the code together. The page is rebuilt from the log and deployed to this site.

The part that keeps it honest

Each project states its non-goals — what it is deliberately not. Drift almost never contradicts a project's purpose; it arrives as a reasonable-looking improvement that happens to serve a different project. Naming the non-goals up front is what makes that visible, so a suggestion that crosses one gets flagged before the work starts rather than discovered three phases later.
